## 3. 生产声明校验：支持什么，拒绝什么

扩展现有闭合解析与计划验证，不调用通用 CMake 求值器来决定“是否安全”。所有新增声明均适用于正式生产路径，不能依赖测试环境标志、项目名称或测试夹具路径豁免。

| 声明 | 本批次允许的形式 | 必须拒绝的形式 |
| --- | --- | --- |
| `target_include_directories` | 已声明目标；明确的 `PRIVATE`/`PUBLIC`/`INTERFACE` 段；有界路径 | 未声明目标、ALIAS/IMPORTED 目标、生成器表达式、未知变量、越界目录 |
| `target_compile_definitions` | 已声明目标；明确作用域；合法宏名及可选的简单字面量值 | 命令/列表展开、生成器表达式、控制字符或能改变解析边界的值 |
| `target_sources` | 已声明目标；明确作用域；存在且归属当前允许源码根的具体源码/头文件 | 文件集高级语法、GLOB、未知变量、外部路径、临时或不存在的源码 |
| `add_library` / `add_executable` | 保留既有支持形式；框架使用静态库和明确源码清单 | 新增动态探测、ALIAS/IMPORTED 绕过、隐式源码搜索 |
| `include` / `add_subdirectory` | 明确文件/目录；有界、只读的基变量展开；下文列明的参数形式 | 系统模块名查找、未知变量、环境变量、越界路径或其他选项 |
| `target_link_libraries` | 已声明、已验证目标；既有认证产物；第 5 节唯一新增系统库绑定 | 任意裸库名、用户指定外部库、链接器标志或隐式库搜索 |

宏值先采用闭合词法：宏名为 ASCII C 标识符；可选值仅为带可选正负号的十进制整数或 ASCII C 标识符。宏声明不得携带 `-D`、空值、引号、分号、反斜杠或 `$`。这足以表达本批次固定框架配置，不承诺字符串宏等更复杂形式。

本批次的 `include` 只接受一个存在的、明确带 `.cmake` 后缀的文件参数，不接受 OPTIONAL、RESULT_VARIABLE、NO_POLICY_SCOPE 或模块查找。`add_subdirectory` 只接受 `source [binary] [EXCLUDE_FROM_ALL]`，每个参数至多一次，拒绝 SYSTEM 和剩余参数。新配方采用这两种形式；不把旧解析器偶然忽略的多余参数视为已支持契约。

解析出的声明必须与实际目标图及构建产物关系一致；File API 中“出现某个目标名”不替代源码声明、目标归属和执行闭包验证。保持 compiler/launcher/plugin 标志的既有拒绝规则和精确的产品插桩例外。

未知命令默认拒绝。`execute_process`、`try_compile`、`try_run`、任意 `configure_file`、函数/宏求值、条件/循环求值、`cmake_language` 和上游模块探测不因本批次获得通用许可。

## 4. 目录上下文、路径与输入绑定

验证上下文分开维护项目源码根、当前源码目录、当前构建目录和当前列表文件目录，不能继续把“正在读取的 CMake 文件目录”用于所有相对路径。

- include 目录的相对路径以当前源码目录为基准，而不是被 include 文件的位置；这是 CMake 的实际语义。[CMake 4.3 官方说明](https://cmake.org/cmake/help/v4.3/command/target_include_directories.html)
- `include` 进入其他列表文件时只更新当前列表目录；返回后恢复。当前源码/构建目录不随 include 文件位置改变。[CMAKE_CURRENT_LIST_DIR 官方说明](https://cmake.org/cmake/help/v4.3/variable/CMAKE_CURRENT_LIST_DIR.html)
- `add_subdirectory` 的源码和构建相对路径分别以当前源码/构建目录解析，递归期间更新两者，返回后恢复。[add_subdirectory 官方说明](https://cmake.org/cmake/help/v4.3/command/add_subdirectory.html)

允许的普通路径变量只有 `${CMAKE_SOURCE_DIR}`、`${CMAKE_CURRENT_SOURCE_DIR}`、`${CMAKE_BINARY_DIR}`、`${CMAKE_CURRENT_BINARY_DIR}`、`${CMAKE_CURRENT_LIST_DIR}`，绑定到服务持有的上下文，不接受项目重赋值。第 5 节的系统库变量是仅限链接参数的独立例外。

仅允许单个已知基变量作为路径前缀，后接字面量路径段，或完全字面量路径。不支持嵌套、多个变量拼接、`$ENV{...}`、生成器表达式和分号列表展开。二进制目录变量不能用来把任意生成文件当成可信源码；产品已有插桩文件仍按原精确认证入口处理。

解析后执行现有规范路径、根归属、文件/目录类型、别名/重解析点及输入身份检查；不得新增任意外部源码根。普通项目文件必须归属项目允许根；框架源码使用已经校验、复制到项目输入区的锁定树。只有第 5 节的单个 SDK 库允许作为额外绑定文件，不能把整个 SDK 目录变成项目源码白名单。

CMake 文件、配方、实际源码与链接输入进入现有快照和启动计划绑定。执行前重新检查身份及摘要；变更、替换、消失或归属变化均拒绝。不能用全局“读过此文件”集合掩盖不同上下文：同一文件以不同目录上下文再次出现时，本批次拒绝；相同上下文可复用绑定结果；递归循环拒绝。

保留现有预算：128 个 CMake 文件、单文件 512 KiB、总计 4 MiB、8192 条命令、65536 个参数、64 个启动计划条目。递归和新增声明共用这些预算，不再另开无限容量。

沿用锁定 CMake 4.3.4；上述官方 4.3 文档用于核对语义，不构成升级要求。

## 5. `winmm.lib`：唯一新增 Windows 系统库绑定

CppUTest 的 VisualCpp 平台实现使用 `timeGetTime`，上游 Windows 核心库链接 `winmm.lib`。仅放行目标声明还不足以保证真实链接成功，裸库名按搜索顺序解析又不能提供确定的来源。

本批次采用服务拥有的只读配置绑定 `UNIT_TEST_IDE_WINMM_LIBRARY`：

1. 从已选工具链实例的验证环境读取 Windows SDK 根、版本及目标架构；不读取父进程环境，不猜安装目录，不选择“最新” SDK。
2. 在该 SDK 的 `Lib/<已选版本>/um/<已选架构>/winmm.lib` 定位唯一文件。确认规范路径、SDK 根归属、常规文件、无路径别名及文件身份，记录 SHA-256。
3. 普通构建与插桩构建使用同一绑定。服务以保留的 configure 参数提供这个绝对路径；调用者、项目变量和 cache 参数均不得覆盖保留名称。
4. 校验器只允许 `${UNIT_TEST_IDE_WINMM_LIBRARY}` 作为 `target_link_libraries` 的完整库参数，且必须匹配服务持有的绑定。不得在 include/source 路径或其他表达式中使用。
5. 实际生成的链接输入必须引用这个绝对文件，启动前复核同一文件身份和字节摘要。仅参数中有变量名或仅 SDK 版本相同不构成证明。

没有合法 SDK 绑定、架构不符、文件变化或实际链接参数转回裸库搜索时均拒绝。不给任意 `.lib`、`/LIBPATH`、PATH/CWD 回退或用户外部库路径开口；不新增可由 IPC 任意填充的库路径字段。

## 7. 生产执行与证据链

按同一条正式路径完成：锁定框架准备 → 用户显式集成固定配方 → 目标/路径/库绑定验证 → 原构建与发现 → 插桩计划验证 → 执行现有测试 → 首份报告入库 → 真实 IPC 文件/函数/行明细 → 生成候选 → 候选真实执行及覆盖率比较 → 用户确认应用 → 一键执行全部测试和重新统计。

报告、源码、工具链、框架、SDK 库、计划和执行快照身份必须一致。保留 APP_ID 进程闭包、受管输出、来源认证、游标/预算和候选不回退要求。

首份报告无可信历史比较时，历史字段仍为 `null`，UI 显示不可比较，不能伪造 `+0`。候选是否提升覆盖率依据它自身的真实执行基线和候选报告判断，不能用历史 `null` 跳过比较。

生成用例继续以可维护源码交付；C++ 应用后新增的 `target_sources` 与 Unity 新测试目标必须重新通过生产图验证。覆盖率 UI 使用真实文件/函数明细，而非替身汇总或读取 SQLite 的测试捷径。

## 8. 失败处理与兼容反馈

缺失 SDK、非法声明/变量、输入变化、图不匹配和预算超限保持失败关闭。内部保留可分类的拒绝阶段与现有安全错误映射，用户诊断描述不支持的集成形式及修正指引；不得泄露绝对内部路径、环境变量或凭据。

不把失败转为 skipped/PASS，不自动扩大白名单，不重写用户源码，不因重试自动改用其他编译器或 SDK。不得提交此前用于定位问题的临时 stderr 诊断扩展。

## 9. 验收门槛与执行顺序

先做最小有效的边界验证，再恢复原生链路；不是重复运行既有任务或盲目多轮 hosted 矩阵。

1. 为已确认不支持的声明保留实际失败证明；新增生产正/反例验证每种作用域、路径上下文及目标关联。包含 `target_sources` 应用后再构建的正例。
2. 安全反例覆盖未知/环境/嵌套变量、生成器表达式、分号展开、不同上下文重复 include、循环、越界/别名路径、未声明/导入/别名目标、非法宏、外部源文件、输入替换和预算超限。
3. 系统库正/反例覆盖已选 SDK/架构唯一绑定、保留变量覆盖、裸库名、搜索路径注入、SDK 或库缺失、库摘要变化及实际链接输入与计划不一致。
4. 固定配方在真实 Windows 工具链上同时通过普通构建、发现、插桩构建和实际测试；证据记录框架源码及配方摘要、SDK 库身份、工具链和产物来源。普通构建成功不能代替插桩成功。
5. 恢复原任务 4：CppUTest 基准夹具首份报告应为行 `5/5`、分支 `2/4`，真实文件和函数分页都有非空行明细；原生 Tree/装饰使用同一存活服务、报告和生成代次，无历史假增量。
6. CppUTest 和 Unity 都运行正式自动生成、候选验证、确认应用和全部测试复跑。基准夹具的分支提升目标为 `4/4`，且原覆盖不回退；该数值是验收目标，尚不是本轮已取得的结果。确认再次打开工程时生成源码可读、可修改、可复跑。
7. 关键本地门槛通过后只跑一次所需跨层收口验证，按实际失败归属修复。任务级审查及整个分支审查完成后才进行已授权推送与 hosted 验收，不用设计文档提交触发矩阵。

本地未提交执行记录不能替代干净提交的验收。最终证据明确区分运行尝试、候选提交、PR head、workflow checkout 与合成 merge SHA；不得将不相同的身份默认为同一来源。
