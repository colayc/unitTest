## 1. 已确认的缺陷与证据边界

2026-10-10 的有界本地诊断使用上述提交导出的首版服务源码、实际 CppUTest 种子及批准的固定 Clang bundle。真实 `Analyzer.Analyze` 返回一个函数、零诊断；该函数为 supported，实际函数绑定成功。随后真实求解器返回零向量、一个诊断、无 Go error。实验在该边界停止，没有执行 oracle、断言、render、apply 或完整 native。

另一项仅调用生产 `parseType("int", nil)` 的定点诊断得到 `Kind=integer`、`BitWidth=0`、`Signed=false`、`Proven=false`。源码检查确认：参数和返回类型都使用该解析器；生产分析包没有补齐整数位宽的后续步骤。求解器的 `finiteDomain` 只接受 8/16/32/64 位整数，拒绝零位宽。这构成可重复的生产者/消费者契约缺口。

现有 `productionPipelineFixture` 直接在手写 Program 中填入 32 位有符号类型，因此未覆盖真实分析器到求解器的交接。此前种子 observer 只证明达到 runner 前置边界，不能证明整数类型信息齐全。

上述两项诊断均以实际 Go exit 1 结束，是诊断断点，不是成功回归。历史 native 的精确首个内部错误和此次求解诊断码未被投影，不倒推或补写。完整诊断见仓库本地 `.superpowers/sdd/2026-10-08-windows-cmake-coverage-compatibility/w4-pipeline-diagnosis-20261010T0943050792390Z.md`，SHA-256 为 `05B23CDA2E486DF27DD244D593291C025F5D4FDFF7CDF873E21E8F977EE5DC71`；它是本地证据，不要求读者在普通仓库克隆中取得该忽略文件。

本设计只解决已确认的整数 ABI 信息缺失，不宣称所有历史失败均由它造成，也不承诺修复后整条生成流水线即成功。

## 2. 方案比较与选择

采用方案 1：每次分析使用同一可信离线 Clang 做一次服务端受控的 ABI 内建宏探测，将目标平台提供的整数事实补入真实 AST 派生的类型，再交给现有求解器。优点是事实随批准的编译器和目标平台取得，不需要另维护 Windows/Linux 类型宽度表；代价是每次 Analyze 增加一个有界编译器进程。

方案 2：维护绑定 manifest 和目标平台的经审核 ABI 表。它无需新增探测进程，但每次平台或编译器变更都需要重新证明和维护对应表。本次不采用。

LLVM 的[固定版本内建宏实现](https://github.com/llvm/llvm-project/blob/ca7933e47d3a3451d81e72ac174dcb5aa28b59d1/clang/lib/Frontend/InitPreprocessor.cpp)根据 TargetInfo 生成整数宽度、大小和范围宏，并根据语言配置生成 plain char 的有符号性标记；[Clang 参数文档](https://clang.llvm.org/docs/ClangCommandLineReference.html#dumping-preprocessor-state)说明 `-dM` 在预处理模式中输出宏定义。这些文档是设计依据，不构成已运行批准 bundle 的新证据。

## 3. 范围与成功标准

仅补齐现有解析器识别的基础整数：`char`、`signed char`、`unsigned char`、`short`、`unsigned short`、`int`、`unsigned int`、`long`、`unsigned long`、`long long`、`unsigned long long`。按照已验证的 AST 类型和对应编译器事实处理，不按主机 Go 类型大小或类型名称猜测位宽。plain char 的有符号性必须来自本次可信编译器配置。

本项不新支持 `size_t` 等别名、浮点类型、枚举、数组/记录布局、类、指针、模板或其他复杂类型；不将已有未证明类型自动转换为基础整数，也不宣称其他类型已修复。已有 bool/void 逻辑和复杂类型安全边界不变。超出上述整数集合的类型不获得新的 ABI 证明，仍服从现有安全限制；需要整数证明但无法取得时拒绝生成。

局部成功标准是：真实 C/C++ 源码分析所得参数、返回值和局部基础整数类型具有一致的、目标平台可证明的位宽与有符号性；真实求解器能对两份现有整数种子生成非空、合法范围内的输入向量；缺失、伪造、矛盾或失效事实仍失败关闭。

待测工程源码、公开头文件、种子函数体、编译快照、框架/CMake 配方、求解算法、预算值、协议、数据库 schema 和 V2 文件不在本项修改范围内。后续生产改动只围绕分析包的事实取得、校验和类型应用及必要回归测试。不新增服务端应用、不下载工具、不改 bundle manifest 信任根。

## 4. 组件边界与正式数据流

在 `testgenanalysis` 内设置独立、私有的整数 ABI 事实解析及应用组件；`Analyzer.Analyze` 只负责协调流程。它不依赖 solver，不提供给协议客户端选择工具、路径、目标或自行声明类型事实的入口。

正式顺序为：既有请求/bundle/编译参数/源码前置校验 → 一次可信 ABI 探测 → 原有真实 AST 分析和来源校验 → 应用整数事实 → 原有源码摘录绑定和最终 Program 摘要封装 → 现有绑定与求解。

- 探测和 AST 分析使用同一已验证的 Clang、resource directory、实际 C/C++ 语言模式及显式空环境。两条调用共同禁用默认配置文件，避免未经绑定的外部配置改变 ABI；这属于服务端固定选项，不扩大输入编译参数语法。
- ABI 探测采用服务端固定的 `-dM -E` 预处理模式、对应 `-x` 语言和已有合法 `-std`，输入为 runner 自有的 EOF 标准输入（`-`），不读取工作区源码、头文件、`-I` 或 `-D`。现有 Windows runner 将 stdin 连接到只读 NUL；Linux 目标进程没有调用者输入。无需创建工作区探测文件或增加 runner 的输入 API。
- AST 调用继续使用原有源码、合法 include/define、`-nostdinc`/`-nostdinc++` 及固定资源头文件。没有源码清洗、头文件闭包豁免、PATH 回退、任意 target、`-m32`、`-funsigned-char` 或额外配置路径。
- 在现有编译参数校验中拒绝重定义本探测依赖的 ABI、编译器身份及平台身份内建宏。拒绝集合就是 ABI 解析器的事实/身份宏集合，不借此禁止无关的普通项目 define，也不接受客户端补传 ABI 值。
- 事实记录仅在当前 Analyze 内有效，绑定本次已验证的 manifest 摘要、语言模式和服务拥有的编译快照身份。不同请求、源文件、平台或并发分析不共用可变事实，不增加跨请求缓存。
- 类型应用同时处理参数、返回值及局部基础整数，保持原有符号、分支、返回表达式和来源。只在证明完整时填写 `BitWidth`、`Signed` 及对应整数 `Proven`；该标记不证明记录布局、指针所有权或算术整体安全。
- 最终封装发生在类型补齐以后，使 Program 摘要覆盖实际交给求解器的类型值；不得复用补齐前的摘要。沿用 IRVersion 1 和现有字段，不新增协议 ABI 字段。

禁止给未证明类型填默认 32 位，禁止依赖平台名称直接推算 `long`，禁止为通过测试而放宽 solver 的合法位宽、算术或范围校验。

## 5. 闭合事实校验、预算与异常

探测 stdout/stderr 分别最多 64 KiB，AST 原有 16 MiB 输出上限保持不变。解析只消费固定白名单的整数事实和身份宏；其余内建宏不进入 IR 或日志。已消费宏不得重复，数值只按约定的整数字面量语法解析，不求值任意宏表达式、不执行输出文本。

必须核对编译器身份、x64 与当前批准的 Windows/Linux 平台身份；必要的字符位数、整数宽度、字节大小、最大值和 plain char 标记必须完整且互相一致。范围与宽度按数学关系校验，有/无符号对以同一基础类型事实为依据；仅接受现有 solver 可处理的 8/16/32/64 位宽。plain char 标记的缺省含义只能在完整、成功且通过身份校验的内建宏输出中解释，不能把截断或缺事实当成“有符号”。

Analyze 为两次编译器调用建立共同的绝对截止时间，不迟于调用者 deadline 或请求 Timeout。探测、AST 均只能使用剩余预算；不能各获得一份新的 30 秒，也不能延长既有 `0 < Timeout <= 30s` 条件。校验之后若已取消/过期，不得继续启动下一进程或返回已封装成功结果。沿用已有 probe 的输出溢出、取消、超时和进程树收敛机制，不增加自动重试。

前后 bundle 验证、源码路径/身份/摘要及 AST 来源/摘录校验全部保留，并覆盖两条调用的整体区间。探测失败、退出非零、超预算、事实缺失/矛盾/重复、身份不匹配或工具/源码变化均拒绝继续生成；不回退到固定表、历史结果或外部工具。

此项沿用既有安全错误边界和 TG1 处理，不新增原始宏、AST、stderr、源码、环境、凭据或协议 body 日志。测试证据只报告必要的闭合事实、测试身份、退出码和预算/拒绝结果。现有 solver/oracle 安全检查不变，本设计不保证后续 oracle 一定能处理所有基础整数表达式。

## 6. 定点回归与真实交接验证

实施时先建立可编译、可执行的行为 RED，再填充生产事实，取得同一测试的 GREEN；编译错误、缺少 bundle、测试跳过或手工填写 Program 不得冒充原缺陷的 RED/GREEN。测试需要隔离首版源码，不能把暂停迁移 022 和其他 V2 脏文件一起编译。

定点覆盖分成以下三个门槛，不默认执行全量测试：

1. 私有事实解析/应用：基础整数映射、plain char 有符号/无符号、Windows/Linux 的不同 long 事实、最大值一致性；缺宏、重复、畸形、矛盾位宽/范围、错误身份、输出截断和未证明别名均不得产生有效证明。合成宏输出可用于解析器单元测试，但不能替代真实生产交接验证。
2. Analyze 协调和安全：探测与 AST 顺序及同一工具/语言/配置、无工作区输入的探测、内建宏重定义拒绝、原源码指令/外来摘录拒绝；工具或源码中途变化、取消、共同截止时间耗尽及并发请求隔离。已有 observer 的断言必须保持“未伪造成功 AST”的含义，不能把 runner 调用计数调整成生产成功证据。
3. 真实源码到求解：使用现有 CppUTest C++17 和 Unity C11 两份种子字节、实际摘要及合法编译参数，调用批准的固定 bundle 上的真实 Analyzer，再将它产生的 Program 交给真实 bounded solver。不得使用 fixture analyzer、伪造 AST 或手填位宽的 Program。分别核对函数绑定、参数/返回整数事实、最终摘要、零失败诊断、非空向量以及向量位于真实整数域内；该测试不执行 oracle、render、生成用例编译、CMake 或完整 native。

普通单元测试不强迫未配置环境启动真实工具；真实交接测试必须显式选定并使用批准 bundle，缺工具或未执行应报告未验证，不能跳过后计作资格 PASS。本地 Windows 先取得真实 C/C++ 交接证据；Linux 共享逻辑有定点解析/隔离检查，但真实 Linux 交接必须由具备批准 Linux bundle 的后续授权环境验证，不能由 Windows 结果代替。

书面计划将给出精确测试名、单次整体上限和 RED/GREEN 命令。所有编译器调用仍受上述原请求预算约束，不运行完整 suite、race、UI、hosted 或 native 来代替局部证明。本设计保存阶段不新增测试实现、不执行任何测试或编译器探测。

## 7. 验收限制与工作区保护

本项局部通过仅代表真实分析到求解的整数契约修复，不代表自动生成/执行/覆盖率维护的整条功能验收、W4、Phase 10、打包资格或上线完成。后续 oracle、断言、render、确认应用、真实用例执行、维护复跑和最终覆盖率仍必须取得各自的新证据。

增加一次有界探测可能增加分析耗时；本设计不承诺消除全部 native 耗时，也不将保护工具摘要复用的其他设计扩展为本项缓存优化。若后续出现不同失败，只依据新的具体边界处理，不放宽当前证明条件。
