## 1. 已验证的问题

本设计处理生产覆盖率读取与自动生成入口之间的契约缺口，不重写生成器。

Foundation [37642606075](https://github.com/colayc/unitTest/actions/runs/37642606075) 的 Linux 生产生成任务在读取首份覆盖率明细时失败。失败 artifact `native-framework-linux-failure`（ID `11494794132`）保留的 SQLite 数据证明：

- coverage run 已完成，`outcome=available`；
- 项目和 `src/classifier.cpp` 的函数明细已持久化，状态为 `current`；
- 行覆盖为 `5/5`、分支覆盖为 `2/4`、函数覆盖为 `1/1`；
- 行命中数与四条分支臂计数均存在；
- 文件 ID `8c41ec4cd1ae1c444276f6fed5c16bab` 和函数 ID `c9096d1efd8a87e00f4cfba79e459610` 均为 32 位十六进制。

三个确定的边界缺口：

1. `internal/session/coverage_detail_routes.go` 的 `detailSummaryProject` 要求可信 `BaselineReportID` 才能返回任何汇总页面；`internal/taskstore/coverage_details.go` 的读取没有提供这个来源。有效绝对覆盖率因此被一起拒绝。
2. 同一 session 文件对所有非空行页面返回 `SERVICE_UNHEALTHY`，因为当前内部页面没有投影协议要求的历史计数和分支统计。删除错误分支而填零不构成修复。
3. `tools/service-probe/src/native-test-generation.ts` 的 `selectNativeGenerationTarget` 使用 64 位摘要规则校验 32 位实体 ID。用 artifact 中的真实 ID 调用当前编译产物，确定返回 `native test-generation coverage target is unavailable`。

原测试替身分别提供了不存在于真实存储读取中的基线来源，以及错误长度的实体 ID。因此局部测试通过不能证明数据库—session—客户端—生成入口已接通。

## 2. 目标和范围

首份完整、来源绑定有效的报告，必须能通过正式 IPC 返回项目、文件、函数及当前行/分支覆盖率。无可信历史基线时，比较值明确不可用；不能把未知比较写成零。

保持现有 Go 本地服务、内置扩展、离线工具链和受管发布架构。生成候选仍必须与自己的真实执行基线比较，证明覆盖率提升且不回退；界面历史增量不可用不能绕过候选验证。

本次不新增历史基线自动选择算法或历史比较持久化。现有存储没有可验证来源的报告，比较值一律不可用，即使已经有多份报告。后续历史比较必须单独补齐来源绑定与一致性验证，不能依靠“上一份报告”猜测。

Windows 普通测试的子进程清理失败、Windows 2022 的 LLVM archive listing 卡住，属于独立诊断项，不混入本设计，也不因本设计通过就宣称整套 foundation 通过。

## 3. 方案和兼容决策

### 方案 1：修正首版 v1.6 明细契约（推荐，待审阅确认）

只修改尚未正式发布的 v1.6 明细字段，服务、schema、生成模型、客户端与内置扩展一起更新。覆盖率 artifact v1.0 以及 Protocol v1.0–v1.5 保持不变。无需新增协议版本或协商分支。

代价：已有 v1.6 候选包客户端不能与新服务混用。新候选包必须绑定同一提交下的扩展、服务与协议资源；旧候选包本身不覆盖更新，也不声称两种 v1.6 明细快照互相兼容。

截至本轮只读核查，GitHub Release 列表为空；这不等于旧候选包不存在。发布候选资格和组件摘要检查仍是必需条件。

### 方案 2：新增 v1.7，冻结现有 v1.6

保留原明细字段，新增能表达未知比较的版本。优点是版本间语义隔离明确；代价是增加模型、协商、路由和旧/新客户端兼容测试。本次首次发布前收口优先采用方案 1，不在本轮直接创建 v1.7。

## 4. 明细字段语义

### 4.1 项目、文件、函数汇总

绝对 `covered`、`total` 保持必填非负安全整数，并继续验证 `covered <= total`。

`coveredDelta` 保持必填，但允许 `null`。三个指标共同遵守：

- 没有可信比较来源：三个 `coveredDelta` 都为 `null`；
- 有可信比较来源：三个值都为有符号安全整数，不能混用数字和 `null`；
- 数字零仅表示已验证的比较确实没有变化；
- `null` 不降低当前报告的 `current` 状态，也不能作为生成候选的增量证据。

nullable 字段必须出现在 JSON 中；Go nil 值序列化为 `null`，不能因 `omitempty` 而消失。TypeScript 对应必填 `number | null`，不能以缺字段表达同一种状态。

本次真实存储读取只输出不可比较状态，不填充不存在的基线 ID。若以后增加数值增量，必须同时提供可验证的报告绑定；仅设置内存中的字符串 ID 不构成持久化证据。

### 4.2 行和分支页面

`line`、`count`、`branchesCovered`、`branchesTotal` 仍是必填的当前证据。历史字段 `baselineCount`、`baselineBranchesCovered`、`baselineBranchesTotal` 保持必填，但允许 `null`；没有可信基线时三者全部为 `null`。

当前分支统计来自同一报告内已验证的持久化分支臂，按函数归属、行、列、ordinal 进行现有规范要求的归属/去重。每条已记录臂计入 total，正命中计入 covered；不能使用历史默认值或根据行命中数推测分支。

文件级和函数级页面都必须从同一读取快照建立当前行/分支统计，并与对应明细汇总一致。不能证明归属或完整性时仍拒绝精确投影，不能把记录缺失自动当成零。只有已验证索引证明该行没有分支时，`branchesTotal=0` 才是有效证据。

保持现有分页、HMAC cursor、报告/源摘要绑定和消息预算。不能通过扩大 wire 上限解决数据建模问题。

### 4.3 实体 ID 与摘要

明确区分两类格式：

- 本次涉及的 file/function/gap/report/run ID：32 位小写十六进制；
- workspace generation、build profile identity、SHA-256：64 位小写十六进制。

验收工具必须使用正确类型的校验器，不接受“32 或 64 都行”。保留精确文件、唯一函数、分页闭合、current 状态及父子身份一致性检查。

不把上述规则泛化到其他实体。现有 test item ID、target identity 等继续按各自既有契约验证。

本设计不重新定义 gap 身份、选择策略或额外增加 gap 生成入口。

## 5. 各层职责与错误处理

- **schema 与模型生成器：**明细字段声明明确的 nullable 语义；同步 Go/TypeScript 模型、validator 与 decoder。既有闭集字段检查不放宽。
- **task store：**读取实际持久化的当前行/分支证据；不存在可信历史证据时保留不可比较状态，不迁移出虚假的基线或增量。
- **runtime/session：**把绝对报告有效性与历史比较资格分开。仍验证报告/项目/代际/源摘要/工具身份、关系约束和分页边界。只移除“无历史基线则绝对明细不可读”的耦合，不绕过其他门禁。
- **test client：**区分 `null` 与数字零，拒绝缺字段、错误类型、混合比较状态、越界计数和身份漂移。
- **Code-OSS：**显示当前 `covered/total` 和可计算的百分比；`total=0` 时百分比显示“不适用”，不作除法。增量为 `null` 时显示“不可比较”，不显示 `+0`，也不把它判定为覆盖率下降。行装饰使用真实当前计数。
- **native probe：**只接收真实协议的 32 位实体 ID，不通过直接读取 artifact 绕过 session；生成及接受仍由正式服务方法执行。

源变化、工具变化、损坏索引、报告不完整、信任撤销、未知字段和非法 cursor 的现有 fail-closed 规则继续保留。不可比较不等于索引损坏，不能用 `SERVICE_UNHEALTHY` 代替正常的缺少历史比较状态。

## 6. 验证策略

按边界依次做红—绿验证，不通过不断重跑全量 hosted matrix 寻找下一个契约错误。

1. **实体 ID：**真实稳定 ID 和 artifact 的 32 位 ID 可被验收选择器接收；64 位摘要、大小写变体、错误父子身份、分页未闭合及多个函数继续拒绝。build profile 仍要求 64 位。
2. **真实 store 到 session：**用生产 SQLite store 写入并读取完整首份报告，不使用带硬编码基线 ID 的正向替身；项目、文件、函数读取成功，当前计数一致，增量为 `null`。
3. **行/分支：**真实 store 的非空 file/function 行页面可读；命中数、分支臂统计和分页正确。首份报告三个历史字段均为 `null`，损坏归属与不一致汇总被拒绝。
4. **协议到客户端：**真实 session 响应通过 schema、生成 Go/TS 模型与客户端 decoder；客户端拒绝缺字段和混合 null/数字。服务端反例证明无来源时不能投影数值零；不能要求客户端仅凭一个零值推断服务器的持久化来源。v1.0–v1.5 回归不改语义。
5. **客户端到 UI：**首份报告能展开项目→文件→函数，显示真实覆盖数和“不可比较”；非空行页面产生真实装饰，不显示虚构 `+0`，未知增量不作为回退证据。
6. **生成闭环：**正式服务从首份报告取得真实 file/function ID，继续分析、候选执行、覆盖率提升验证、用户确认及接受后的重跑。不得为了得到历史基线多跑一次相同 coverage，也不允许宽松重试掩盖持久性失败。
7. **提交前检查：**生成文件一致性、受影响 Go/Node/扩展测试及针对共享状态的 race 回归。需要的全量验证只做一次，记录完整退出码；不把部分测试通过写成整套通过。
8. **hosted：**本地契约测试通过后再推送代码提交，用现有授权运行正式 workflow。成功证据绑定新的候选 SHA；Windows 独立阻塞未闭合时不宣称整体通过。

## 7. 完成标准和发布边界

- 首份完整报告的项目、文件、函数、非空行/分支页面通过真实 store、正式 IPC 与客户端读取。
- “未知历史比较”和“验证后零变化”可明确区分，无假的基线/增量字段。
- native probe 使用真实实体 ID；生成候选的真实增量验证没有放宽。
- 扩展显示真实覆盖率与不可比较状态，保留已有分页和安全失效行为。
- 检查记录区分本地验证、hosted 结果与尚未关闭的问题，不把静态 PASS 当成产品可用。

本设计通过不代表 Phase 10 全部完成，也不关闭历史比较功能或 Windows 两个独立阻塞。PR #39 暂不合并，不发布 GitHub Release，不启用签名，不修改 master。
