# 统一可维护用例、手动向导与离线数据输入设计

日期：2026-10-09

状态：两部分呈现设计已获用户确认；本书面设计等待用户复核；尚未实施。

范围：完整产品扩展的首个子项目，不是全部新增需求的完成声明。

## 1. 目标与已确认选择

在现有完全离线、无 Mock/Stub 的 C/C++ 测试链路上增加统一用例定义，使自动生成、图形化手动设计和离线数据输入能够共用身份、输入、预期结果、维护、执行和结果关联机制。生成的测试仍是可维护、可实际编译执行的 C/C++ 源码。

用户已确认以下选择：

- 数据交换采用本地文件导入／导出，不提供网络上传／下载，不新增内网或云端服务器。
- 采用统一用例模型，不以独立的源码编辑器或数据表建立另一套执行系统。
- 自动、手动、导入用例复用现有驱动生成、构建、执行和覆盖率基础能力。
- 用户修改测试代码后，重新生成必须保护修改并显示冲突，不能直接覆盖。
- 区分生成成功、执行成功、断言通过和正确性依据；观察到的输出不能自行成为正确答案。
- 一键执行必须显示通过、失败、受阻和禁用数量，并显示实际文件／函数覆盖率。
- 本批离线输入采用版本化 JSON，单批最多 1000 条、文件最多 8 MiB。

产品仍由 Code-OSS 桌面程序、内置扩展、现有 Go 本地服务、本地 IPC 和固定工具包组成。这里的“无需服务器”指不需要额外部署网络服务，不是删除内置本地服务。

## 2. 本批范围及完整需求映射

本批实现统一定义和三个输入入口的贯通，以及维护、真实执行、结果和已有覆盖率的关联。它不重新开发现有分析器、测试框架或覆盖率采集器，也不把旧组件存在等同于当前完整验收通过。

## 3. 组件边界

### 3.1 统一定义与版本存储

使用现有本地持久化架构增量保存定义、不可变版本和转换记录，与“已接受源码／验证凭证”注册表分开。定义至少包含以下语义字段：

- 项目、规范化源文件及服务签发的文件／函数身份；
- 稳定场景身份和用例编号；
- 按真实参数类型排序的输入及必要的已支持对象构造数据；
- 预期目标、类型化预期值、比较规则及来源；
- 创建来源、定义版本、内容摘要及来源绑定；
- 启用状态、草稿版本和已接受版本的独立引用；
- 接受后的实际测试路径、块摘要和验证／发布凭证关联。

草稿无需伪造已接受块或验证凭证。已接受版本不能因保存新草稿而被替换。修改请求必须绑定预期版本；并发或过期修改产生冲突，不采用最后写入覆盖。

### 3.2 三个输入适配器

自动入口把现有求解器候选转换为统一定义，不修改原有自动验证要求。手动入口收集服务签发对象身份及闭集类型化数据。数据入口解析有界本地 JSON，并生成导入预览；不执行文件内的表达式、脚本或命令。

三个入口都调用服务端定义校验，不独立拥有驱动、编译器调用、发布器或覆盖率存储。扩展只负责表单、预览和用户确认，不签发正确性证明或接受资格。

### 3.3 校验、渲染、发布与运行

复用并明确扩展现有类型校验、受管身份、渲染、三方维护、原子文件发布及构建／执行接口。手动预期结果和手动用例准入需要独立凭证语义，不能把导入值直接塞入现有可信证明字段。

运行协调器冻结实际选择的已接受版本、测试源码和构建配置，收集真实执行及覆盖率结果。结果查看器使用这份运行绑定，不从草稿或旧报告推断当前通过状态。

### 3.4 能力协商与兼容

新增协商式用例设计能力和有界类型化路由；旧服务未广告能力时隐藏新编辑入口，保留原有协议语义和流程。不以客户端兼容为由跳过服务端验证或抬高既有 wire 上限。具体路由和 DTO 在实施计划中依据现有协议风格落定，但本节的信任边界不可改变。

## 4. 身份、维护与状态

用例身份与可编辑内容版本分离。现有自动场景沿用既有身份；新增手动场景在创建时获得稳定场景身份，修改输入或预期结果只增加版本。当前渲染器把候选向量身份用于受管场景，必须通过明确兼容适配接入新定义，不能假定修改输入后现有渲染接口自然保留编号。

源文件／函数重绑定不是普通字段编辑；身份不匹配、对象删除或签名改变时必须重新验证或显示过期／失去关联。旧用例编号和已接受源码不做隐式批量迁移。不从任意历史 C/C++ 测试源码强行重建结构化定义。

结构化定义决定下一次生成意图；实际已接受且当前的源码快照决定运行了什么。维护时继续比较上次接受、当前文件和新生成候选三个版本：

- 块外用户代码保持不变。
- 块内修改不能被自动覆盖，必须进入三方差异审查。
- 用户可明确采用生成版本、保留当前内容或转为手写维护。
- 不能可靠回写结构化字段的源码修改显示“代码已手改／结构化视图不可回写”，不能声称向导完整还原了任意代码。
- 转为手写维护后，原有普通测试流程仍按其安全规则运行；不能借此把未知源码重新标为经过统一模型验证的用例。

模型状态和执行结果不是一个字段。定义可处于草稿、待确认或已接受；绑定可为当前、过期、冲突、失去关联或无效；运行可通过、断言失败、构建失败、崩溃、超时、取消或不完整。已接受并不等于断言通过。

## 5. 手动向导与离线 JSON

### 5.1 手动向导行为

向导按以下流程工作：选择项目内的服务签发函数 → 展示支持状态、参数和返回／输出目标 → 编辑类型化输入及预期值 → 保存草稿 → 验证并预览代码 → 明确接受 → 一键执行。

只显示实际支持的类型、目标、比较规则和构造方式。整型按真实位宽、符号和范围校验，采用无精度丢失表示；浮点规则含明确容差，禁止无界或非有限值。布尔、枚举及已证明安全的数组／结构体沿用现有严格边界；不加入任意 C/C++ 表达式、地址或未经建模的类初始化代码。

本设计规定行为和校验，不要求重新设计既有覆盖率树或结果视图，也不预选无关视觉布局。

### 5.2 文件契约

基线格式是 UTF-8 版本化 JSON 用例定义文档，格式版本为 1。一个文档绑定一个活动项目及可重新核对的源文件／函数；包括类型化定义、稳定场景和版本来源信息，不携带可直接信任的发布或运行凭证。

- 单文件最多 8 MiB，单批最多 1000 条；既有更严格的单值、类型、渲染和协议上限仍生效。
- 闭集字段、重复键检测、有界嵌套、重复编号检测及真实参数类型检查必须在服务接受前完成。
- 未知格式版本／字段、非法范围、错误类型、越界路径、身份不匹配或不支持的构造拒绝导入提交，并展示有界原因。
- 本地文件由用户选择。文件内路径不是新的访问权限；所有对象重绑定依据服务维护的活动项目，不自动跨项目映射。
- 文件读取不触发源文件修改或执行。校验通过只形成预览；用户确认后事务性保存草稿。校验／冲突失败不产生半批已接受用例。
- 相同身份、相同规范化内容的再次导入是无操作；同编号内容不同必须审查冲突并绑定当前版本，不能静默替换。
- 导出默认包含当前选择的定义及其版本标识；如果导出的是草稿，明确标注，不假装是已接受版本。
- 导入文件中的“已证明、已通过、覆盖率”声明不能授权本地接受；必须重新校验。来源标签不能改变已有用例的服务端准入策略。

8 MiB 是本地文件总量，不是单条 IPC 消息上限。导入会话使用受限分页／分块并绑定整批摘要及计数；完整校验前不提交，取消和断线不形成部分接受。导出也必须冻结一致的版本集合，不能拼接不同时间的分页。

批量传输默认每项目最多一个活动会话，服务同时最多四个会话；每个会话最多暂存 8 MiB，总暂存不超过 32 MiB。单消息（含包装后）不超过 256 KiB 或协商 wire 上限中的较小值。自创建起最多存活 10 分钟，到期清除暂存并拒绝旧会话提交；这不是后续编译／运行任务的执行预算。导入与导出共享这些并发和暂存上限，不用分页绕过总量限制。现有更严格限制优先，取消、断线、重启不得恢复为自动提交。

本批不包含 CSV、Excel、ZIP 或网络传输适配器。这里的 JSON 定义文件不等于完整驱动、输入、结果和覆盖率证据包。

## 6. 预期结果及准入策略

### 6.1 正确性依据

明确区分三种来源：经过服务核验的源代码／契约依据、用户明确指定的预期结果、仅观察到的输出。

用户预期需要绑定用例版本、真实输入、源快照、预期目标和比较规则；即使实际输出匹配，也只能称“符合用户指定预期”，不能升级为独立证明。导入预期经明确审查后同样属于用户指定来源。

只有观察结果、没有可靠或用户指定预期的定义保持草稿／观察信息状态，不自动形成正确性断言，不计为通过。本批不新增自动把观察结果当作判据的运行模式。

### 6.2 自动用例

现有自动补覆盖率路径保留有效断言、通过真实执行及已有套件验证、至少一种目标覆盖率提高、无覆盖率回退等现有门槛。未通过自动门槛的候选不能通过更改标签得到自动接受；服务端创建来源和凭证策略不能由客户端覆盖。

### 6.3 手动／导入用例

显式用户设计走独立类型化预期和准入凭证，不要求正向覆盖率增量。这是有意扩展现有行为，不是声称当前自动 publisher 已支持。

准入必须完成能力／安全校验、真实 configure／compile／link、可归属执行结果、当前源与定义版本绑定，以及明确源码差异确认。文件发布可共享现有原子机械机制，但不能复用或伪造自动路径的通过／覆盖率资格凭证。

若真实执行完成且可归属地出现断言不匹配：

- 保存定义和 FAIL 结果，不当作生成器错误或自动删除用例。
- 用户可在清楚看到已知 FAIL 的前提下明确确认保留编译可执行的测试。
- 确认绑定该用例版本、源码、结果和差异摘要，不能覆盖后来的失败或不同源快照。
- 已知 FAIL 接受不能掩盖既有用例新增失败；其他回归结果仍独立报告和审查。
- 接受后的记录仍是“已接受源码、断言 FAIL”，不是成功自动候选，也不是通过资格。

构建错误、崩溃、超时、收集不完整、取消或清理不确定性不是可接受的已知断言 FAIL。不能证明上述区别及准入凭证时保持草稿，不降级走宽松自动路径。完整手动用例验收必须证明该新路径实际成立，草稿兜底不算功能完成。

## 7. 一键执行与覆盖率

一键执行冻结启用、当前、已接受、可执行用例的版本清单，并在运行前核对源／测试源码／工具链／配置。新草稿不会静默代替已接受版本；存在待发布修改时明确显示运行哪个版本。

界面显示请求、可执行、已执行、通过、失败、受阻和禁用数量及原因。启用但因过期、冲突、缺少预期或不支持而受阻的用例使批次不完整；即使可执行子集全部通过，也不能显示整个请求全部通过。没有可执行用例是空／受阻运行，不是 0 条测试全部通过。

禁用必须在真实框架执行选择中生效，不能只从统计中隐藏已执行用例。保持已有回归套件的真实运行和结果；运行清单必须区分模型用例与既有手写测试，不能用模型筛选缩小生产覆盖率分母或掩盖套件失败。无法落实框架级真实选择时，不能广告启用／禁用能力为已完成。

使用现有可信构建、进程监督、结果收集和覆盖率采集。结果区分断言 FAIL、编译／链接错误、崩溃、超时、取消和数据不完整；缺失或损坏凭证不能显示 PASS。取消完成必须以进程及清理证据为依据，不凭请求已发送就宣称停止。

文件／函数视图绑定真实运行、源码、构建与采集器身份，展示现有函数／行／分支指标。相同源与采集语义的结果才能比较增量；无法归属的数据标为不完整，不伪造百分比。

一次断言 FAIL 的运行若产生完整有效覆盖率，可以显示为该失败运行的覆盖率，但不能称为通过验收的覆盖率。收集不完整时标为不完整；保留上一份有效报告作为历史，不能让旧 PASS 覆盖最新运行的失败结论。源码变化后旧视图标为过期。

行覆盖率不等于真正语句覆盖率，分支覆盖率不等于 MC/DC；本批不新增或改名这两项指标。

## 8. 安全、恢复及兼容规则

- 保留完全离线、无 Mock/Stub、工作区信任、源身份、工具链新鲜度及进程隔离边界。
- 表单和数据包不提供任意源码、命令、argv、环境变量、绝对主机路径或指针地址执行权限；用户在编辑器维护代码仍受现有运行规则约束。
- 预览／确认／执行之间发生源、定义、测试、配置或工具链漂移时使凭证过期，禁止按旧预览写入。
- symlink、reparse point、路径穿越、别名或越界目标按现有安全规则拒绝。
- 所有运行失败保留草稿、用户源码及历史报告；发布只能改明确确认的测试／配置目标，不修改生产源码。
- 文件与数据库更新通过凭证绑定的持久 journal 协调恢复；单纯数据库事务不被描述为跨文件系统原子更新。未决发布不标为当前／已接受，不在重启后自动确认草稿。
- SQLite 增量迁移必须保留旧数据及旧功能。新能力不完整或迁移失败时不广告新入口，不进行危险协议降级。
- 诊断不输出源码、用例值、绝对路径、环境变量、token 或无界原始输出。预览和用户主动导出的用例数据属于明确的产品内容通道，不能混入普通日志。
- 不改变正式签名、许可审批、releaseReady 或发布资格。

## 9. 验收与验证策略

实施按新增边界选择针对性测试，先验证契约及负向行为，再完成真实集成。每个小任务不重复无关全量 native 矩阵；最终功能验收也不能被单元测试或假进程结果替代。

必须取得以下证据：

1. 三个入口对相同类型化定义使用相同规范化规则、身份与执行映射；旧自动路径保持门槛不变。
2. 修改输入／预期后编号保持稳定、版本增加；服务重启后身份、草稿和已接受引用正确恢复。
3. JSON 导出再导入保留定义，重复导入不增加副本；大小／数量边界、重复键、非法类型、版本、路径、身份和并发冲突被拒绝，源文件零意外写入。
4. 用户预期和观察输出不能伪装为独立证明；手动正常通过和已知断言 FAIL 均有真实可归属结果及正确准入行为。
5. 源码手改后再生成完整保留用户内容；冲突未解决不发布；草稿保存不改正在运行的已接受版本。
6. 禁用真正停止所选模型用例的执行；受阻、空集合、部分执行、FAIL 和基础设施错误均不显示全批 PASS。
7. 取消、断线、进程清理不确定性和文件／DB 发布中断不能形成假的当前／已接受状态；重复确认幂等。
8. 老服务／能力缺失保留旧行为并隐藏新入口；协议分页和文件总量限制均有效。
9. 真实 C/Unity 和 C++/CppUTest fixture 完成“手动创建 → 验证预览 → 接受 → 执行 → 查看文件／函数覆盖率”，并验证导入、编辑、重复生成、已知 FAIL 和重启维护路径。
10. 覆盖率与实际源和运行一致，旧／失败／不完整报告正确展示。最终声明支持的 Windows/Linux 配置各有真实证据；一个平台或框架的结果不能推广为全部通过。
