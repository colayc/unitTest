# Phase 10 生产测试生成的阶段检查点修复设计

日期：2026 年 10 月 11 日。

状态：用户已确认方案 1，即修正生产驱动与校验器的阶段契约，保留通用执行器、状态机和数据库约束。本轮只保存设计；书面设计确认后编写实施计划，暂不实施。

## 目标与失败边界

修复第一版自动生成测试用例流程中，生产校验器返回下一工作阶段、而执行器要求返回已完成阶段所造成的状态跳跃。目标是让真实生产适配器能够按合法检查点完成验证、最小化和等待确认，或者正常拒绝没有有效候选的结果。

代码基线为 `e87c26ed82377295290e2fa579c8faf4f0bd768b`，工作分支为 `codex/phase10-production-generation`。这属于既有 Phase 10 生成链路，不是暂停的第二版需求；涉及的执行器、驱动、校验器与状态图在本次工具摘要优化提交中没有变化。

已有隔离 Windows CppUTest 验收在验证阶段报 `TG1:validating:transition:invalid_transition`，持久化事件停在 `rendering` 后转为 `failed`。任务创建至结束约 149 秒，未达到 300 秒预算，未进入等待确认、应用用例与维护验收。

源码可确定两种验证返回值都与该时刻的检查点不一致：`rendering` 只能转到 `validating`，校验器却返回 `minimizing` 或 `rejected`。最小化还存在相同的提前返回，且生产驱动缺少 `awaiting_confirmation` 分支。已有验收没有记录当次验证返回值，因此不把具体保留或拒绝分支、拒绝原因认定为已获实测证明。

本设计不承诺修复后该 native 场景一定产生有效用例或通过全流程。合法的 `rejected` 与基础设施失败必须保持区别。

## 方案选择

采用方案 1：让生产驱动与校验器服从现有已完成阶段契约，单独补齐等待确认工作。改动集中在生产适配层及相关测试，保持其他驱动的执行语义。

不采用方案 2：将通用执行器改为进入阶段时提交检查点。这会改变恢复含义、事件与预算记账，还会影响既有驱动，超出定点修复范围。

不能把允许跳过状态、提前存入最小化 ID、增加超时或重试当作修复。`ValidTransition`、`NextStage` 和 taskstore 的检查点限制均保持原样。

## 阶段契约

持久化状态表示已经完成的工作；`NextStage` 决定下一项工作。生产适配器的返回值必须是本次工作完成后的合法状态，而不是提示执行器下一步去哪里。

| 调用前持久化状态 | 本次工作 | 正常返回与检查点 | 持久化数据 |
| --- | --- | --- | --- |
| `rendering` | 真正执行验证 | `validating` | 保留的候选及其源码和验证证据；没有保留候选时为空 |
| `validating` | 判断是否存在有效候选并完成最小化 | 有候选为 `minimizing`，确认零候选为 `rejected` | 不提前保存最小化 ID 或预览 |
| `minimizing` | 构造待确认的候选集合与预览 | `awaiting_confirmation` | 最小化 ID 与预览身份在同一检查点保存 |

成功路径为 `rendering → validating → minimizing → awaiting_confirmation`。没有有效候选的路径为 `rendering → validating → rejected`。真实错误仍通过现有失败或取消路径结束，不伪装成验证完成或业务拒绝。

数据库目前不允许在 `minimizing` 状态保存非空 `MinimizedCaseIDs`。本设计遵守这个限制，也保留等待确认时必须存在权威候选、预览差异及确认摘要的规则。

## 组件职责

### 生产驱动

`productionGenerationDriver.RunStage` 继续先执行真实目标解析，保留当前工作区、报告、源码、工具与请求身份校验以及原绝对截止时间。分析、求解和渲染阶段的既有行为不变。

验证、最小化和等待确认分别调用对应的生产适配器操作。新增独立的内部预览操作，接口仅用于本地生产连接，不增加公开协议或客户端选项。驱动不得通过直接改写任意返回状态掩盖错误的适配器结果。

最小化和等待确认依赖已经提交的候选与验证证据，不依赖之前的流水线内存缓存。服务恢复后不能为了重建预览重新运行分析、渲染或完整候选验证。早期阶段仍沿用原流水线；本修复不将其缓存改为跨任务权威。

### 生产验证适配器

真正验证仍保留配置、编译、链接、发现、执行及覆盖率收集，以及独立断言或特征化断言的原有证明规则。

验证保留候选时，返回 `validating`，连同原有一个候选及对应源码、验证证据交给通用执行器事务提交。当前一版即使生成多个函数的测试，也聚合为一个候选；不在本轮加入多候选选择策略。

验证完成但没有保留候选时，同样返回 `validating`，不携带候选、源码或验证证据，并清除本次运行的适配器内存记录。验证执行发生错误、取消或超时则保持错误返回，不使用零候选结果代替错误。

### 最小化与预览适配操作

最小化只处理可信的 `validating` 检查点。已完成验证且候选数量为零、没有矛盾的生成证据或预览数据时，返回 `rejected`。状态不对、记录无效、候选数量与证据不一致或正候选证据缺失时必须报错，不能作为零候选拒绝。

存在候选时，按当前一版规则核对唯一候选、绑定、源码与验证凭据，确认最小化选择，返回 `minimizing`。该返回不携带新的候选或产物，也不携带供执行器提前落库的最小化 ID 与预览。

预览操作只处理可信的 `minimizing` 检查点，重新从同一持久化候选与证据确定当前一版的唯一选择。选中的 ID 必须确实属于本次运行，并与候选、源码和绑定一致，不能仅依赖内存中的上次选择。返回 `awaiting_confirmation`、真实候选集合和选中的 ID。

当前唯一候选规则使最小化后的选择可以从已保存候选确定地重建，不需要新数据库字段或提前保存 ID。多候选或无法唯一重建的情况拒绝成功；不能默认为全部保留。

### 持久化证据读取

最小化与预览共用窄职责的证据恢复与核验逻辑。仅允许读取当前运行已拥有、已在检查点登记的源码和验证证据，按现有完整检查核对 task 与 run 所有权、产物类型、摘要、规范编码、请求快照、目标绑定、阶段凭据、用例 ID、源码及计划编辑。

对正候选不能只按可预测的 ID 查找任意产物；不能把仅已写入磁盘、尚未被运行检查点拥有的文件当成权威输入。内存命中不能取消检查点所有权、当前目标与凭据有效性校验。

不会新增持久化结构、改变证据版本或采用部分字段解码代替已有严格恢复检查。无法恢复同一证据就失败，不重建或替换证据以继续。

## 通用执行器与安全约束

保留 `generationService.run` 的单次阶段预算预留、绝对时间约束、合法转换检查、修订号 CAS、候选与产物事务提交及事件发布流程。每个检查点仍只提交一次；冲突不能覆盖较新的结果，不增加自动重试。

进入等待确认时，仍由执行器调用既有 `authoritativeSet` 读取并核验持久化候选，调用发布器 `Plan` 重新构造预览，校验非空差异与摘要。适配器提供的 `PreviewSet` 不替代这条权威路径，不能用空占位集合让阶段通过。

最小化 ID 与执行器计算的预览身份一起保存后，才执行既有 managed review finalizer。用户确认、发布器接受、生成用例应用和维护路径不改动，也不在预览阶段写入用户源码或测试文件。

请求超时、候选上限、并发上限、预算记账和 Windows 工具摘要保护边界不放宽。最小化和预览不新增外部工具进程，也不重复消耗生成候选与产物预算。取消后不得成功提交或进入等待确认。

## 断点恢复与既有失败任务

从 `validating` 恢复时，读取已提交的候选及证据：可信零候选走拒绝，正候选走最小化。候选或证据损坏走失败，不能重新执行完整验证或采用旧内存记录继续。

从 `minimizing` 恢复时，按同一持久化证据重建当前一版唯一选择，核验后构造预览并进入等待确认。恢复不提前发布文件，不增加额外检查点，不依赖新增数据库字段。

已经处于 `awaiting_confirmation` 的运行保留原恢复与 review finalizer 行为。历史 `failed`、`rejected`、`accepted` 或 `cancelled` 任务不修改、不复活；此前 native 的工作区、数据库和失败记录继续保留。

## 定点验证与验收标准

实施先获得行为 RED，再使用同一明确选择器获得 GREEN。缺少方法造成的编译失败、空选择器或测试没有运行不能作为行为 RED。

关键回归必须连接真实 `generationService`、生产驱动、生产验证适配器和 SQLite 检查点，而不是只测试返回预设正确状态的替身校验器。外部工具可使用已有受控测试夹具；不运行生产 LLVM、CppUTest 或 Unity native 验收。

必要验证为：

- 真实生产适配链的保留候选路径完整经过三个合法检查点，最后具有真实最小化 ID、预览与可维护 review；没有提前存入 ID、跳过阶段或重跑验证。
- 不保留候选时先提交 `validating`，再合法拒绝；没有用例、源码或验证证据被错误保留，不记录 `invalid_transition` 基础设施失败。
- 清空驱动与适配器缓存并重新打开隔离服务和数据库，分别从 `validating`、`minimizing` 恢复，结果及选择身份保持一致。
- 缺失、篡改、错归属、未登记或绑定变化的候选和证据均拒绝成功，零候选与损坏证据不能混淆。
- 每个新增边界保留取消、超时、过期目标和凭据错误；检查点修订号冲突不覆盖结果、不重复发布或运行工具。
- 事件序列、预算消耗、外部验证调用次数与预览构建次数符合上述契约。非法适配器返回仍被通用执行器拒绝。
- 原有失败诊断、阶段顺序及数据库禁止提前写入最小化 ID 的定点用例保持通过；不通过修改这些断言放宽约束。

测试使用独立第一版源码快照与全新临时数据库，不将暂停的 V2 taskstore 修改及 migration 022 带入本轮测试。旧完整测试证据不整批重跑；并发与 CAS 验证也使用定点选择器。

验收结论仅覆盖阶段契约及上述恢复、安全回归，不代替真实生成、应用、一键执行、覆盖率提升与用例维护的 native 全流程验收。后续 native 必须另行取得有界授权，使用新构建、新工作区和新数据库，不修改旧尝试凭据或自动重试。
